## 0. 5분 안에 알아야 할 것

### 다섯 개의 개념

| 개념 | 무엇인가 |
|---|---|
| **VOC** | 하나의 Managed System에 대한 하나의 피드백. 리포터에게 보이는 상태와 내부 처리 상태를 **따로** 갖습니다. |
| **Finding** | 근거에 기반한 판단. "사람들이 이렇게 말한다"에서 "그래서 뭘 해야 한다"로 넘어가는 다리입니다. |
| **Task Request** | 실행 작업 후보. 검토를 거치지 않은 것이 백로그에 바로 쌓이지 않게 막는 장치입니다. |
| **Task** | 실제 실행 작업. 리포터에게 보이는 것과 **독립된** 자체 상태를 갖습니다. |
| **Entity link** | 위 항목들 사이의 저장된 연결. 추적 경로를 실제 데이터로 만드는 것이 이것입니다. |

### 두 가지 원칙 — 먼저 알고 시작해야 덜 헤맵니다

**1. 리포터 상태와 내부 상태는 자동으로 연동되지 않습니다.**
Task를 `released`로 옮겨도 연결된 VOC가 저절로 `resolved`가 되지 않습니다. 실수가 아니라 의도된 설계입니다 — "Task 완료"가 항상 "문제 해결"은 아니고, 자동 전파는 감사 기록을 건너뛰면서 리포터에게 잘못된 안심을 줍니다. **릴리스는 후보를 만들 뿐이고, 확정은 사람이 합니다.**

**2. 권한이 없을 때 화면은 비어 있지 않고 경로를 알려줍니다.**
막힌 영역은 승인된 요약이나 "접근 요청" 버튼을 보여줍니다. 그러니 **권한이 없다고 보이면 대개 요청할 수 있다는 뜻**입니다. [9번](#9-권한이-없다고-나온다)을 보세요.

### 화면 구조

왼쪽 레일이 큰 영역(Home · VOC · Findings · Tasks · Integration · Surveys · Admin)이고, 그 옆 사이드바가 해당 영역의 세부 화면입니다. 사이드바 위쪽의 **Managed System 선택기**는 필터가 아니라 **권한 범위**입니다 — 내 권한 밖 시스템을 고르면 화면이 그에 맞게 제한됩니다.

## 1. 겪은 문제를 알리고 싶다

**누구나 할 수 있습니다.** 권한이 따로 필요 없습니다.

`New VOC`(`/vocs?action=create`)로 갑니다.

적어야 하는 것:

| 항목 | 필수 | 메모 |
|---|---|---|
| Managed System | 필수 | 어느 시스템 얘기인지. 이 선택이 이후 담당자·권한 범위를 결정합니다. |
| 제목 | 필수 | 200자까지 |
| 상세 설명 | 필수 | 서식·목록·링크를 쓸 수 있는 편집기입니다 |
| Analytics Area | 선택 | 분석 영역을 알면 지정, 모르면 비워도 됩니다 — 트리아지에서 채워줍니다 |
| 소스 맥락 | 선택 | 직접 사용 중 겪었는지, 남의 얘기를 대신 올리는지 등 |
| 첨부 | 선택 | 스크린샷·로그 |

**Managed System을 고르면 오른쪽에 비슷한 VOC가 뜹니다.** 같은 얘기가 이미 있으면 거기에 붙는 편이 훨씬 빨리 처리됩니다 — 중복은 나쁜 게 아니라 신호지만, 이미 진행 중인 건에 얹으면 담당자가 맥락을 다시 파악할 필요가 없습니다.

> **팁 — 상세 설명 칸이 안 눌리는 것 같다면** 예전 버전 얘기입니다. 지금은 편집기 박스 어디를 눌러도 활성화됩니다.

## 2. 내가 올린 건이 어떻게 되고 있는지 보고 싶다

`My VOCs`(`/vocs?view=my`)에 내가 올린 것만 모입니다.

**리포터에게 보이는 상태**는 여덟 단계입니다:

```
received → reviewing → assigned → progress → prep → resolved
                                                      ↕
                                              reopened / closed
```

이 상태는 **담당자가 직접 바꿉니다.** 뒤에서 Task가 어떻게 굴러가든 자동으로 움직이지 않습니다([0번 원칙 1](#두-가지-원칙--먼저-알고-시작해야-덜-헤맵니다)). 그래서 상태가 바뀌었다면 누군가 그렇게 판단했다는 뜻이고, 대개 **공개 업데이트가 같이 달려 있습니다.**

상세 화면에서 볼 수 있는 것:

- **공개 타임라인** — 담당자가 리포터에게 남긴 업데이트와 내 답장
- **연결된 Task** — 내 제보가 실제 작업으로 이어졌다면 여기 보입니다. 권한에 따라 전체가 보이거나, 공개 가능한 요약만 보이거나, 아예 안 보입니다.

**답장을 쓰려면** 상세 화면의 리포터 답장 편집기를 쓰세요. 내부 코멘트와는 **물리적으로 다른 입력창**입니다 — 리포터가 볼 것과 내부용은 절대 섞이지 않습니다.

## 3. 들어온 VOC를 처리해야 한다

**필요 권한:** 해당 Managed System에 `voc.triage`. Admin은 역할만으로 가집니다.

### 어디서 보나

| 화면 | 용도 |
|---|---|
| `Inbox` (`/vocs?view=inbox`) | 내 범위의 전체 VOC |
| `Triage` (`/vocs?view=triage`) | **처리 대기 큐.** 여기가 실제 작업 공간입니다 |
| `High severity` / `Unassigned` / `No follow-up` | 트리아지 큐의 저장된 관점. 사이드바 숫자가 남은 건수입니다 |

### 트리아지에서 정하는 것

VOC를 고르면 오른쪽 패널에서 판단합니다:

- **심각도** — low / medium / high / critical
- **담당자** — 개인 또는 팀 (**둘 다 지정할 수는 없습니다**)
- **Analytics Area** — 분석 영역 연결
- **처리 상태** — `untriaged` → `triaged`, 정보가 부족하면 `needs_more_information`, 실행할 것이 아니면 `dismissed_not_actionable`

**변경은 즉시 반영되고 4초 동안 되돌릴 수 있습니다.** 토스트의 되돌리기를 누르면 원복됩니다. 4초가 지나면 다시 바꾸면 됩니다 — 재판단을 막는 규칙은 없습니다.

### 이미 판단한 건을 다시 바꾸려면

VOC 상세 패널의 트리아지 영역에서 **`트리아지에서 변경`** 버튼을 누르면 해당 VOC가 선택된 채로 트리아지 콘솔로 이동합니다. 상세 패널 자체는 읽기 전용입니다.

### 내부용 메모

**내부 코멘트** 편집기는 리포터에게 보이지 않습니다. 판단 근거, 확인한 것, 담당자 간 논의를 여기 남깁니다. 리포터 답장·공개 업데이트와 나란히 있지만 **셋은 서로 다른 입력창**이고 절대 합쳐지지 않습니다.

## 4. 리포터에게 상황을 알려야 한다

**공개 업데이트**가 리포터에게 보이는 유일한 창구입니다. 그리고 **리포터 상태를 바꾸는 경로이기도 합니다.**

여기가 핵심입니다: 상태를 바꾸면 시스템이 **공개 업데이트를 쓰든지, 건너뛰는 이유를 적든지** 둘 중 하나를 요구합니다. 리포터 몰래 상태만 바뀌는 일은 생기지 않고, 건너뛴 경우에도 이유가 감사 기록에 남습니다.

즉 실무에서는:

- **상태를 바꾸며 설명한다** → 공개 업데이트를 쓰고 새 상태를 함께 지정
- **상태만 바꾼다** → 건너뛰기를 고르고 사유 기재 (기록에 남습니다)

작성 전에 미리보기로 리포터에게 어떻게 보이는지 확인할 수 있습니다.

## 5. 같은 얘기가 반복해서 들어온다

`Clusters`(`/voc-clusters`)에서 여러 VOC를 하나로 묶습니다.

클러스터는 `draft`로 시작해 `confirmed`가 됩니다. 초안 동안 구성원을 넣고 빼며 정말 같은 문제인지 확인하고, 확정하면 그 묶음이 이후 근거의 단위가 됩니다.

클러스터로 묶으면 좋은 이유:

- **한 번에 공개 업데이트를 보낼 수 있습니다** — 같은 문제를 제보한 사람들에게 같은 소식을 각각 쓰지 않아도 됩니다
- **Finding의 근거가 튼튼해집니다** — "한 명이 불편하다고 했다"와 "열두 명이 같은 걸 말했다"는 다른 판단을 낳습니다
- **클러스터에서 바로 Task Request를 올릴 수 있습니다**

## 6. 근거를 모아 판단으로 남기고 싶다

**필요 권한:** `finding.read` / `finding.manage`. Admin은 역할만으로 가집니다.

`Findings`(`/findings`)로 갑니다. Finding은 **"근거를 보니 이렇다"는 판단**이고, 실행 요청의 출발점입니다.

만들 때 적는 것: 제목, 요약, 심각도, 확신도(low / medium / high), 대상 Managed System, 필요하면 Analytics Area.

**출처는 두 가지입니다:**

- **VOC에서** — 특정 VOC를 근거로
- **설문 응답에서** — 승인된 발췌만 사용합니다. 익명 응답이나 신원 보호된 응답은 **가려진 뒤 명시적으로 승인**되어야만 근거로 붙습니다

Finding 상태는 `draft` → `active` → `converted`(실행으로 넘어감) 또는 `not_actionable` / `archived`입니다.

Finding 상세에서 **근거를 더 붙이거나**(Add Evidence / Link Existing Evidence) **연결된 VOC·Task로 바로 이동**할 수 있습니다.

> **확신도를 낮게 적는 걸 두려워하지 마세요.** `low`로 적힌 Finding은 "더 봐야 한다"는 정직한 신호이고, 나중에 근거가 쌓이면 올리면 됩니다.

## 7. 실제로 고치는 일로 넘기고 싶다

### 왜 바로 Task를 못 만드나

**Task Request**를 거치게 돼 있습니다. 검토되지 않은 후보가 백로그를 채우면 백로그가 우선순위 신호로서 의미를 잃기 때문입니다.

### 흐름

```
Finding / VOC / Cluster
        │
        ▼
   Task Request  ──►  pending_review  ──►  approved  ──►  converted (Task 생성)
                            │                              또는 기존 Task에 연결
                            ├──►  needs_more_evidence  (근거 보강 요청)
                            └──►  rejected
```

`Task Requests`(`/tasks?view=requests`)에서 검토합니다. 승인·반려·근거 보강 요청 중에 고르고, 승인하면 Task로 전환하거나 이미 있는 Task에 연결합니다.

**자기가 올린 요청을 자기가 승인하는 경우**(self-approval)는 워크스페이스 정책이 허용할 때만 가능하고, 감사 기록에 별도 라벨이 붙습니다. 필요 권한은 `task_request.self_approve`이며 Admin은 역할만으로 가집니다.

### Task 다루기

`Tasks`(`/tasks?view=board`)는 칸반 보드입니다. 카드를 끌어 상태를 옮깁니다.

```
backlog → todo → doing → review → done → released
                                            ↕
                                        reopened
```

`My Tasks`(`/tasks?view=my`)에 내게 배정된 것만 모입니다.

Task 상세의 **Linked context**에서 이 작업이 어느 Finding에서 나왔는지 보이고, 클릭하면 그 Finding으로 갑니다.

> **다시 강조 — `released`로 옮겨도 VOC 리포터 상태는 바뀌지 않습니다.** 리포터에게 알리려면 해당 VOC로 가서 [공개 업데이트](#4-리포터에게-상황을-알려야-한다)를 쓰세요. 번거로워 보이지만, 이것이 "배포했으니 해결됐다"고 잘못 통보하는 것을 막습니다.

## 8. 고친 뒤에 정말 나아졌는지 확인하고 싶다

**필요 권한:** 읽기는 `survey.read`, 만들고 운영하는 것은 `survey.manage`. Admin은 둘 다 역할로 가집니다(단, 해당 권한에 **명시적 거부**가 걸려 있으면 거부가 이깁니다).

`Surveys`(`/surveys`)로 갑니다.

### 수명 주기

```
draft  ──►  open  ──►  closed
(편집 가능)  (응답 수집)  (결과 확정)
```

**`draft`일 때만 질문을 편집할 수 있습니다.** 열고 나면 문항이 고정됩니다 — 응답 도중에 질문이 바뀌면 결과를 해석할 수 없기 때문입니다. 질문 순서 변경, 추가, 삭제 모두 초안 단계에서 끝내세요.

### 결과 보기

`/surveys/{id}/results`에서 집계를 봅니다. 여기에 **익명성 규칙**이 걸려 있습니다:

- **응답이 5건 미만인 구간은 표시되지 않습니다.** 필터를 걸어 대상을 좁혔을 때도 마찬가지입니다.
- 필터를 이리저리 바꿔가며 빼기로 특정인의 응답을 역산하는 것도 막혀 있습니다.
- **Workspace Admin이라고 이 기준이 완화되지 않습니다.**

**개별 응답 원문**을 보려면 `survey.read_personal_responses`가, 내려받으려면 `survey.export`가 따로 필요합니다. **이 둘만은 Admin도 역할로 우회할 수 없고 명시적 권한을 받아야 합니다.** 개인이 식별될 수 있는 데이터라서 그렇습니다.

자유 응답을 Finding 근거로 쓰려면 **가림 처리 후 승인**을 거쳐야 발췌가 붙습니다.

## 9. 권한이 없다고 나온다

정상적인 흐름입니다. 이 제품은 **권한을 미리 다 주지 않고, 필요할 때 요청받는 방식**입니다.

### 화면이 보여주는 네 가지 상태

| 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| 정상 표시 | 권한 있음 | — |
| 승인된 요약만 | 전체는 못 보지만 안전한 요약은 볼 수 있음 | 전체가 필요하면 요청 |
| **접근 요청** 버튼 | 요청할 수 있음 | 사유를 적고 요청 |
| 차단 안내(요청 불가) | 명시적으로 거부됐거나 요청 대상이 아님 | 관리자에게 문의 |

### 요청하고 승인받기

1. 막힌 화면에서 **접근 요청**을 누르고 사유를 적습니다. 민감한 권한은 사유가 **필수**입니다.
2. Admin이 `/admin/permissions/requests`에서 검토합니다. 승인 / 반려 / 추가 정보 요청 중에 고릅니다.
3. 승인되면 해당 Managed System 범위로 권한이 생깁니다.

### Admin이 스스로에게 권한을 주는 경우

가능하지만 그냥 되지는 않습니다. 워크스페이스 정책이 self-approval을 허용해야 하고, 승인 시 **근거 정책 조항과 사유를 함께 입력**해야 하며, 감사 기록에 `SELF_APPROVAL` 라벨이 붙습니다.

즉 Admin이 설문 관리 권한이 필요하면 — 본인이 요청하고 본인이 승인하되 **왜 그랬는지가 남습니다.**

### 알아둘 것

- **명시적 거부는 무엇보다 우선합니다.** 역할이 admin이어도, 다른 곳에서 권한을 받았어도 거부가 이깁니다.
- **권한은 Managed System 단위입니다.** A 시스템의 `voc.triage`가 B 시스템에는 적용되지 않습니다.
- 사이드바의 Managed System 선택기에서 권한 밖 시스템은 아이콘으로 표시됩니다.

## 10. 워크스페이스를 관리해야 한다

**Admin 전용** (`/admin/*`).

| 화면 | 하는 일 |
|---|---|
| **Managed Systems** (`/admin/managed-systems`) | 시스템 등록·보관, 기본 담당자/검토자 지정 |
| **Analytics Areas** (`/admin/analytics-areas`) | 시스템 하위 분석 영역 관리 |
| **Permission requests** (`/admin/permissions/requests`) | 권한 요청 검토 |
| **Workspace settings** (`/admin/settings`) | 운영 정책. self-approval 허용 여부 등 |

**기본 담당자를 지정해 두면** VOC와 Finding 생성 시 자동으로 채워집니다. 다만 **기본값이 채워졌다는 것이 트리아지가 끝났다는 뜻은 아닙니다** — 담당자만 정해진 미처리 상태가 만들어질 수 있으니 큐를 계속 보세요.

**Managed System을 보관(archive)하면** 그 아래로 새 VOC·Finding·설문을 만들 수 없습니다. 기존 데이터는 남습니다.

## 11. 자주 막히는 지점

**Task를 옮겼는데 리포터 화면이 그대로다**
설계된 동작입니다. 해당 VOC에서 [공개 업데이트](#4-리포터에게-상황을-알려야-한다)를 써야 리포터 상태가 바뀝니다.

**설문 질문이 수정이 안 된다**
설문이 이미 `open`입니다. 문항은 `draft`에서만 편집됩니다.

**설문 결과가 비어 있다**
해당 구간 응답이 5건 미만일 수 있습니다. 필터를 풀어 보세요. Admin이어도 이 기준은 같습니다.

**Admin인데 권한이 없다고 나온다**
`survey.read_personal_responses`와 `survey.export`는 Admin도 명시적 권한이 필요합니다. 또는 해당 권한에 **명시적 거부**가 걸려 있을 수 있습니다.

**담당자를 개인과 팀 둘 다 지정하려는데 안 된다**
하나만 됩니다. 다운스트림이 담당자 한 명을 확정할 수 있어야 하기 때문입니다.

**트리아지 변경을 되돌리고 싶다**
4초 안에 토스트의 되돌리기를 누르세요. 지났으면 그냥 다시 바꾸면 됩니다.

**"링크를 복사하지 못했습니다"가 뜬다**
브라우저가 클립보드 접근을 막는 환경(사내 IP 접속 등)입니다. 주소창의 URL을 직접 복사하세요. **복사되지 않았는데 성공이라고 표시되지는 않습니다.**

## 12. 참고 — 역할과 권한 실측표

### 역할

| 역할 | 무엇을 하는 사람인가 |
|---|---|
| **Admin** | 워크스페이스 전체 권한. 설정, 권한 승인, 시스템 등록, 운영 정책 |
| **Developer** | 하나 이상의 Managed System 범위를 가진 실무자. 트리아지, Finding, Task 실행 |
| **User** | 제보하고 자기 건을 추적. 트리아지 불가 |
| **Reporter** | 역할이 아니라 **관계**입니다 — 특정 VOC를 올린 사람. 역할과 무관하게 자기 VOC에 대해서는 리포터입니다 |

### 데모 시드(`SEED_MODE=personas`) 권한

| 액터 | 역할 | 부여된 권한 |
|---|---|---|
| Mock Admin / Mock Admin Two | admin | 별도 부여 없음 (역할 기반 권한만) |
| Mock Developer One | developer | **tableau**: `voc.read` `voc.triage` `finding.read` `finding.manage` `survey.read` `task_request.self_approve` |
| Mock Developer Two | developer | **power-bi**: `voc.read` `voc.triage` `finding.read` `survey.read` `survey.manage` |
| Mock User / Mock User Two | user | 없음 |

### Admin이 역할만으로 갖는 것

`workspace.read` · `workspace.admin` · `voc.triage` · `voc.read` — 그리고 도메인 모듈이 얹는 것들:

| 권한 | Admin 우회 |
|---|---|
| `finding.read` · `finding.manage` · `task_request.self_approve` | 있음 (거부보다도 우선) |
| `survey.read` · `survey.manage` | 있음 (단 **명시적 거부가 이깁니다**) |
| `survey.read_personal_responses` · `survey.export` | **없음 — 명시적 권한 필요** |

권한 판정의 최종 근거는 언제나 백엔드입니다. 화면 표시는 힌트일 뿐입니다.
