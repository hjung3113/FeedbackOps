FeedbackOps Workflow Proposal

cmux 4-pane × Claude(설계·리뷰) × Codex(구현) — 속도↑ 퀄리티 유지

1. 진단 — 왜 느려졌나

증상원인비용
이슈당 사이클이 길다 Required Reading 10개 + per-issue 브랜치/PR/머지 + 직렬 강제 P3 cleanup도 P1과 같은 오버헤드
병렬 인프라 미활용 cmux claude-teams, .claude/worktrees/ 존재하나 단일 pane만 사용 독립 P3 14개가 줄 서서 대기
설계·구현·리뷰가 한 컨텍스트 모델 한 대가 전부 처리. 큰 컨텍스트 누적 → 느린 응답·환각 증가 이슈 후반부 품질 저하
검증이 사후 "complete" 외친 뒤 PR review에서 잡힘 리뷰 라운드 늘어남
P3 묶음이 N개 PR "per-issue feature branch" 룰 P3에도 적용 14 P3 = 14 PR review 부하

2. cmux 4-pane 역할 분할 (워크스페이스 1개)

데모: workspace:16 "WF-4role-demo" 에 실제 생성 완료. 각 pane은 독립 셸 + 독립 컨텍스트.

┌──────────────────────────────┬──────────────────────────────┐ │ ARCHITECT (Claude Opus) │ CODEX (codex exec) │ │ pane:38 / surface:70 │ pane:40 / surface:71 │ │ 설계 · 이슈 dispatch · grill │ 구현 · diff 생성 · 단순 fix │ ├──────────────────────────────┼──────────────────────────────┤ │ REVIEWER (Claude Sonnet) │ VERIFIER (shell · CI) │ │ pane:39 / surface:72 │ pane:41 / surface:73 │ │ /code-review · 보안 · 룰 │ pnpm test · run · playwright│ └──────────────────────────────┴──────────────────────────────┘
① ARCHITECTClaude Opus 4.7
  • 이슈 읽고 스코프 결정 (티어링 표 적용)
  • 필요 시 grill-me / writing-plans
  • 구현 프롬프트 작성 → CODEX pane에 dispatch
  • worktree 분기, 브랜치 네이밍
  • 여러 이슈 묶기 결정 (배치 PR)
② CODEXcodex exec
  • ARCHITECT가 준 spec 그대로 구현
  • codex exec "<prompt>" 비대화 모드
  • diff 생성 → codex apply 또는 직접 commit
  • 스코프 외 변경 금지 — 룰은 ARCHITECT가 강제
  • 의문 생기면 STOP, ARCHITECT에 보고
③ REVIEWERClaude Sonnet 4.6
  • CODEX diff에 /code-review 즉시 실행
  • AGENTS.md 룰 vs diff 대조 (모듈 경계, 사본 verbatim)
  • 도메인 invariant 위반 검출
  • fail → ARCHITECT에 reroute, pass → VERIFIER로
  • PR 직전 /security-review
④ VERIFIERshell · headless
  • pnpm test --filter ... 영향 받은 패키지만
  • typecheck, lint
  • FE 변경 시 /run + Playwright snapshot
  • 실패 로그 ARCHITECT로 → 수정 사이클
  • green 확인 후 PR 생성 신호
핵심: 4 pane = 4 컨텍스트 분리. ARCHITECT 컨텍스트가 구현 노이즈로 오염되지 않음. CODEX는 좁은 spec만 받음 → 환각 감소. REVIEWER는 diff만 보고 룰 체크 → 빠름.

3. cmux 명령 cheatsheet (이 워크플로우 전용)

워크스페이스 셋업 (이슈 시작 시)

# 새 worktree 워크스페이스 만들기
cmux new-workspace --name "issue-31-idem-audit" \
  --cwd "/Users/hyojung/Desktop/2026/FeedbackOps"

# 4-pane 분할
cmux new-split right --surface <left>
cmux new-split down  --surface <left>
cmux new-split down  --surface <right-top>

# 역할 라벨
cmux rename-tab --surface <s1> "ARCHITECT"
cmux rename-tab --surface <s2> "CODEX"
cmux rename-tab --surface <s3> "REVIEWER"
cmux rename-tab --surface <s4> "VERIFIER"

Pane 간 dispatch

# ARCHITECT → CODEX 로 작업 던지기
cmux send --surface <codex> \
  'codex exec "Fix issue #31: idempotency replay must bump audit_log. See apps/backend/src/modules/voc/idempotency.ts. Add test in *.spec.ts."'
cmux send-key --surface <codex> Enter

# VERIFIER 에 테스트 트리거
cmux send --surface <verifier> \
  'pnpm --filter backend test idempotency'
cmux send-key --surface <verifier> Enter

# 결과 읽기 (ARCHITECT가 polling)
cmux read-screen --surface <verifier> --lines 40

알림 · 자동화

# CODEX 끝나면 ARCHITECT pane 깜빡임
cmux trigger-flash --surface <architect>

# 또는 명시 알림
cmux notify --workspace workspace:16 \
  --title "CODEX done" --body "issue-31 diff ready for review"

# 백그라운드 빌드 결과 신호
cmux wait-for build-green --timeout 300

8. End-to-end 한 이슈 흐름 예시 (#31)

  1. ARCHITECT: 이슈 #31 읽고 티어링 → P3 Trivial. git worktree add ../wt-31 feature/31-idem-audit
  2. ARCHITECT: spec 한 단락 작성 → CODEX pane에 send: 
    codex exec "In apps/backend/src/modules/voc/idempotency.ts,
when replay hits cached response, also write audit_log row with
action='idempotent_replay'. Add spec asserting audit_log count
increments. Touch only this file + its *.spec.ts."
  3. CODEX: diff 생성 → commit
  4. REVIEWER: git diff HEAD~1 + /code-review → AGENTS.md 룰 체크
    • 모듈 경계 OK? repo만 audit_log 씀?
    • 테스트 invariant 닿음?
  5. VERIFIER: pnpm --filter backend test idempotency + typecheck → green
  6. ARCHITECT: 같은 모듈 #30, #27 묶을지 결정 → 묶으면 2~5 반복 후 1 PR
  7. ARCHITECT: PR body 작성 → gh pr create → develop merge

기존 흐름: 한 모델이 1~7 전부 + 컨텍스트 누적. 신규 흐름: 4 pane 분업, 총 wall-clock ↓, 컨텍스트 깨끗.
