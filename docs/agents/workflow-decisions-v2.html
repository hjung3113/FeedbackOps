1 JSON I/O Format

DECIDED JSON = canonical source of truth. Markdown = rendered view (선택 사항, 사람용).

모든 에이전트 간 아티팩트는 *.json 으로 쓰기. 필요 시 사람용 *.md 자동 생성.

PR-DRAFT.json 스키마 (top-level)

field설명
schema_version형식 버전. 마이그레이션 안전성.
artifact_type"pr_draft" | "review" | "blocker" | "touch"
issue이슈 번호, 제목, 라벨
branch브랜치 이름, base
summary한 단락 요약
scopeallowed / forbidden 파일·디렉토리
acceptance_criteriaAC 항목 배열 (id, statement, met:bool)
implementation_notes왜 이렇게 구현했는지
files_touched경로 + 변경 종류 (add/edit/delete)
tests새/수정 테스트 파일, run 명령
risks알려진 위험 배열
deviations프롬프트 대비 의도된 일탈 + 사유
review_requestsREVIEWER에게 특별히 봐달라 요청할 영역
handoffcommit SHA, verify output 경로

Tradeoff

  • JSON 승: diff 도구, 스키마 검증, 라우팅, 대시보드, 장기 안정성
  • MD 승: 빠른 사람 스캔
  • 결정: JSON canonical → 필요시 scripts/render-artifact.ts로 MD 생성

2 CONDUCTOR Agent (5번째 역할)

DECIDED FEASIBLE EFFECTIVE CONDUCTOR 추가. Claude Opus 4.7 1M-context.

위치 · 권한

속성결정
위치전용 pane (별도 워크스페이스 X). 이유: cmux send로 다른 pane들에 직접 접근 가능, 워크스페이스 분리 시 통신 마찰
모델Claude Opus 4.7 1M-context
역할전체 flow 컨텍스트 보유, phase 요약 누적, 직렬/병렬 결정, task 분할, role 배정, 모델 선택, persona 결정
권한읽기/리뷰만. 제품 코드 직접 편집 금지. ARCHITECT가 그 다음 단계.
요약 주기매 material event 직후 (이슈 완료, BLOCKER, review reject, cluster 시작/종료)

새 계층 구조

┌─────────────────────────────────────────────────────────────┐ │ CONDUCTOR (Opus 4.7 1M) ← user의 단일 대화창 │ │ ├─ 전체 phase 요약 누적 │ │ ├─ 직렬/병렬 의사결정 │ │ ├─ role/model/persona 할당 │ │ └─ ARCHITECT(들)에게 task 디스패치 │ │ │ │ │ ▼ │ │ ARCHITECT (Opus) — cluster 단위 dispatcher │ │ │ │ │ ┌───────┼──────────┐ │ │ ▼ ▼ ▼ │ │ CODEX REVIEWER VERIFIER (VISUAL-REVIEWER opt.) │ └─────────────────────────────────────────────────────────────┘

실패 모드 (CODEX가 식별)

  • Stale summaries — phase 요약이 오래되어 현실과 괴리. 매 material event 후 강제 업데이트로 완화.
  • Over-centralized bottleneck — 모든 결정이 CONDUCTOR 통과. ARCHITECT 자율 영역 명시 필요.
  • Hallucinated worker state — CONDUCTOR가 worker 진행을 추측. 해결: 모든 상태를 JSON artifact에서만 읽기.
  • Role bleed — CONDUCTOR가 슬슬 코드 편집 시작. 강한 룰: read-only.

의도 달성 분석

  • Context rot 방지: ✓ — CONDUCTOR가 요약만 보유, worker context는 매 task 후 reset 가능
  • 효율성: ✓ — 전체 그림 보고 직렬/병렬 최적화, 중복 작업 방지
  • 위험: 단일 실패점. CONDUCTOR pane 죽으면 전체 stop. → JSON artifact가 disk에 있어 복구 가능.

4 Review = Checklist + Smoke Test

DECIDED 체크리스트 = REVIEWER 작성 (AC + 프로토타입 + invariants에서 유도). Smoke = 터치된 flow + 인접 1개 regression path만.

책임 분배

작업소유자비고
이슈 AC seedARCHITECTFULL 템플릿에 명시
리뷰 체크리스트 작성REVIEWER독립 derivation 필수 — AC만 베끼지 말 것. invariants, 프로토타입, 터치된 파일에서 자체 항목 추가.
일회성 smoke 스크립트REVIEWER이 PR 전용. 보관 X.
재사용 Playwright specVERIFIERrepo 영구 보관. CI에서 실행.
Playwright 환경 셋업VERIFIERdocker-compose, fixtures, seed

Smoke 범위

  • 매 PR: 터치된 user flow 1개 + 인접 regression path 1개
  • 금지: 매 PR마다 full user journey (너무 느림, 시그널 약함)
  • Full journey: slice 완료 또는 release gate에서만

체크리스트 항목 (REVIEWER가 derive)

  1. 이슈 AC 각 항목 → met/unmet 표시 (PR-DRAFT의 acceptance_criteria 검증)
  2. AGENTS.md 모듈 경계 룰 위반?
  3. 프로토타입 verbatim copy 일치?
  4. invariants (VOC 출처, Task 분리 등) 침범?
  5. 테스트가 behavior 검증인가, 구현 검증인가?
  6. scope 외 파일 변경 있는가?
  7. smoke flow 1개 + regression 1개 통과?
