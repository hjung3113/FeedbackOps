✓ DECIDED · 7 합의 사항

D1

역할 권한 (Authority)

ARCHITECT = sole dispatcher.
REVIEWER는 CODEX에 직접 지시 X.
Why: 단일 task authority. 충돌하는 지시 루프 방지.
D2

프롬프트 템플릿 2종

MINIMAL (P3) · FULL (P1/P2)
MINIMAL 필드: issue, task, scope, accept, verify, handoff. FULL 추가: branch, read-first, constraints (invariants/ADRs/copy), commit msg, ambiguity rule.
D3

ARCHITECT 필수 입력 (3개)

1. Priority class (P1/P2/P3)
2. Locked boundaries (files + ADRs)
3. Success contract (AC + verify cmd)
Why: CODEX가 이슈만으로는 추론 불가. ARCHITECT가 매번 강제.
D4

핸드오프 채널 = 파일

.review/ISSUE-N-PR-DRAFT.md (CODEX → REVIEWER)
.review/ISSUE-N-REVIEW.md (REVIEWER → ARCHITECT)
.review/ISSUE-N-BLOCKER.md (CODEX abort)
Why: diffable, pane/session loss에도 생존, 기존 .review/ 패턴 재사용. notify=ephemeral, trailer=cramped 탈락.
D5

실패 모드 — abort no-commit

ambiguity 발견 → 커밋 안 함 + BLOCKER.md 작성
Why: partial commit = review noise + 가짜 완료 신호. clean abort > messy progress. BLOCKER.md 필수: 시도 명령, 블로커, 터치된 파일(이상적으론 0), 추천 결정 2-3개.
D6

Review-Reject 루프

REVIEWER 파일 작성 → ARCHITECT 읽음 → CODEX에 patch 재프롬프트
Why: REVIEWER가 CODEX에 cmux send 절대 금지. ARCHITECT만 CODEX가 듣는 목소리.
D7

병렬 클러스터 조정

Declared touch sets (.review/ISSUE-N-TOUCH.md) + ARCHITECT 직렬화
직렬화 대상: packages/shared/*, migrations, shared UI, shared fixtures, global docs. 워크트리는 브랜치만 격리, semantic merge conflict는 못 막음.

flow 합의된 흐름

┌──────────────────────────────────────────────────────────────────┐ │ ARCHITECT picks issue → writes prompt (MINIMAL or FULL) │ │ │ │ │ │ cmux send → CODEX pane │ │ ▼ │ │ CODEX: implement │ │ ├─ success → commit + write .review/ISSUE-N-PR-DRAFT.md │ │ └─ ambiguity → ABORT (no commit) + .review/ISSUE-N-BLOCKER.md │ │ │ │ │ │ signal (commit OR blocker file present) │ │ ▼ │ │ REVIEWER reads diff + PR-DRAFT.md │ │ ├─ pass → notify ARCHITECT → VERIFIER runs tests → PR create │ │ └─ fail → .review/ISSUE-N-REVIEW.md │ │ │ │ │ ▼ │ │ ARCHITECT reads REVIEW.md → re-prompts CODEX with patch ──┐ │ │ │ │ │ ┌─────────────────────────────────┘ │ │ ▼ │ │ (loop until pass) │ └──────────────────────────────────────────────────────────────────┘

? OPEN · 5 남은 결정 사항

Q1. .review/ 디렉토리 — git에 커밋할지?
A커밋 (history 추적, PR에 포함)
Bgitignore (로컬 ephemeral)
Lean: Slice 3 기존 패턴이 commit이라 A 유력. 단 PR diff 커질 수 있음 — 별 PR로 분리하거나 squash 시 drop 룰 필요.
Q2. REVIEWER pane 위치 — 같은 worktree vs base worktree?
A같은 worktree (live diff, 즉시성)
B별도 worktree on base (atomic snapshot, commit 단위 리뷰)
Lean: 이전 토론에서 B 합의. half-written state 안 봄, base 컨텍스트 같이 봄.
Q3. ARCHITECT pane 자동화 여부
AInteractive (user가 직접 ARCHITECT와 대화)
Bcmux send 받는 자동화 (마스터 오케스트레이터 pane 별도)
Lean: 초기엔 A로 시작 → 패턴 검증 후 B 점진 도입. 처음부터 자동화는 디버깅 어려움.
Q4. PR 생성 — 어느 pane?
AARCHITECT (의도 작성자가 PR body 마무리)
BVERIFIER (green 직후 자동)
Lean: A. PR body = ARCHITECT 컨텍스트가 가장 풍부 + 클러스터 묶음 결정 직접. VERIFIER는 green 신호만.
Q5. Parallel worktree 상한
A2 (보수적, context 여유)
B3 (현재 제안)
C4+ (공격적, ARCHITECT가 과부하 가능성)
D제한 없음 — touch-set 충돌로 자연 직렬화
Lean: B (3). 인지 부하 + 화면 분할 + ARCHITECT가 3 worktree 추적 가능 한계. 4+는 context 누수 위험.
